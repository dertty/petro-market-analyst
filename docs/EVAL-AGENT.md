# Оценка ответов агента: golden dataset и методика метрик

Документ описывает, как измерять качество **ответов агента целиком** — в дополнение к
`scripts/eval_rag.py`, который оценивает только ретривер. Датасет — в
`reports/golden_agent_dataset.jsonl`, раннер — `scripts/eval_run.py`. Здесь методика:
у каждой метрики указано, из какого поля записи и какого поля API она считается.
Как из этих метрик собирается оценка прогона и как выносятся экспертные вердикты —
в `EVAL-RUBRIC.md`.

## 1. Датасет

Файл: `reports/golden_agent_dataset.jsonl` — 34 записи, 5 сценариев:

| scenario | n | Что проверяет |
|---|---|---|
| `rag` | 8 | Ответ на основе отчётов из RAG-индекса (3 отчёта SberCIB) |
| `web` | 6 | Ответ на основе веб-поиска (актуальность, не покрытая отчётами) |
| `hybrid` | 6 | Комбинированный: база из отчёта + актуальность из веба |
| `forecast` | 7 | Вызов расчётного модуля (`forecast` / `supply_shock`) |
| `out_of_scope` | 7 | Корректная обработка запроса вне компетенции |

Принципы наполнения:

- **rag/hybrid** строятся только на фактах, уже размеченных в retrieval-сете
  `reports/golden_dataset.jsonl` (связь через `retriever_ids`): эталоны не выдуманы, а при
  провале e2e-вопроса видно, находил ли фрагмент сам ретривер.
- **web** не содержит эталонных чисел — котировки дрейфуют; проверяется процесс
  (инструменты, маркировка `[источник, web]`, дата среза). Датасет не протухает.
- **out_of_scope** — градиент: бытовые вопросы (ноль вызовов инструментов) и «граничные»
  темы соседних рынков (допустим `rag_search` с честным «не найдено» — это негативы
  retrieval-сета `neg-001/002/005`).
- Ответ может собираться из **нескольких чанков и страниц** (запись `rag-008` — из двух
  документов), поэтому проверки фактов идут по тексту итогового ответа, а не по чанкам.

### 1.1. Схема записи

Обязательны `id`, `scenario`, `question`; остальные поля опциональны по сценарию.

| Поле | Тип | Семантика |
|---|---|---|
| `tools_required` | list[str] | Каждый должен встретиться среди вызванных инструментов |
| `tools_forbidden` | list[str] | Ни один не должен быть вызван |
| `rag_before_web` | bool | Первый вызов `rag_search` раньше первого `web_search` (по `ts` событий) |
| `max_web_searches` | int | Максимум вызовов `web_search` (контракт промпта — 2) |
| `expected_facts` | list[obj] | Факты, обязанные быть в тексте ответа (см. 1.2) |
| `expected_citations` | list[obj] | Ожидаемые цитаты (см. 1.3) |
| `forecast_expect` | obj | Ожидаемый вызов расчётного модуля (см. 1.4) |
| `refusal_expect` | obj | Критерии корректного отказа (см. 1.5) |
| `implicit` | bool | Неявный триггер инструмента: несовпадение аргументов — warning, не fail |
| `retriever_ids` | list[str] | `id` записей retrieval-сета — источник эталонных фактов/страниц |
| `reference_answer` | str | Эталон для экспертной оценки (для rag — из `relevant_text` retrieval-сета) |
| `judge_criteria` | list[str] | Бинарные критерии экспертной оценки (см. 3.3) |
| `notes` | str | Служебный комментарий, в проверках не участвует |

### 1.2. Семантика `expected_facts`

Проверяются по **сырому markdown ответа** (поле `result` задачи Ouroboros, не `answer_html`).

- `{"kind": "number", "value": V, "tolerance": T, "context_regex": R}` — найти все совпадения
  `R` в ответе; в окне ±150 символов вокруг каждого извлечь числовые токены
  (`\d+(?:[.,]\d+)?`, запятая = десятичный разделитель); pass, если хоть один токен
  попадает в `[V−T, V+T]`. Окно решает проблему «15 — это дисконт, а не страница».
- `{"kind": "regex", "pattern": P}` — `re.search(P, answer)` не пуст.
- `{"kind": "substring", "text": S}` — `S in answer` (регистрозависимо; в датасете обрезанные
  основы вроде `"Роснефт"`, чтобы покрыть падежи).
- `unit`/`desc` — документация для человека, кодом не проверяются.

### 1.3. Семантика `expected_citations`

Формат цитаты из отчёта генерируется кодом (`skills/petro_rag/lib/search.py:52-58`):
`[<report>, <date>, с. <N>]`, где `<report>`/`<date>` — из `reports/manifest.yaml`.
Извлечение цитат из ответа:

- report-цитата: `\[[^\]]+, \d{4}-\d{2}-\d{2}, с\.\s*\d+\]` — отбор по форме, без фильтра по
  издателю: иначе ссылка с выдуманным названием не разбирается и проверка на галлюцинации
  проходит вхолостую;
- web-маркер: regex `\[[^\]]+,\s*web\]`.

Варианты записи в датасете:

- `{"kind": "report", "document": "<имя pdf>", "pages": [..]}` — в ответе есть цитата этого
  документа (report+date из manifest) хотя бы с одной из перечисленных страниц. Если
  ожидаемых документов несколько (мультидокументные вопросы) — процитирован каждый.
- `{"kind": "report", "min_count": N}` — хотя бы N валидных report-цитат любого документа
  (для hybrid-вопросов, где факт есть в нескольких отчётах).
- `{"kind": "web", "min_count": N}` — хотя бы N web-маркеров.

**Валидность** проверяется всегда, независимо от ожиданий записи: каждая report-цитата
в ответе обязана матчиться на пару report+date из `manifest.yaml`. Цитата, которой нет
в манифесте, — **галлюцинированная**; целевое значение по прогону — 0.

### 1.4. Семантика `forecast_expect`

- `tool` — какой инструмент ожидается (`forecast` | `supply_shock`).
- `args` — подмножество аргументов вызова, обязанное совпасть с фактическими `args`
  события (`benchmark`/`horizon` или `cut_mbd`/`offset_mbd`). При `implicit: true`
  несовпадение аргументов — warning.
- `must_mention_method` — в ответе назван хотя бы один метод (chronos / ETS / Хольт /
  случайное блуждание / rw_drift).
- `must_mention_interval` — в ответе есть «80 %» или «q10»+«q90» и **обе** числовые границы.
- `must_mention_range` (supply_shock) — приведён диапазон цен (min–max по веткам эластичностей).
- `must_mention_elasticity_source` (supply_shock) — упомянут источник допущений
  (литература по эластичностям / поле `elasticity_source` инструмента).

### 1.5. Семантика `refusal_expect`

- `max_tool_calls` — суммарное число событий `tool_call` ≤ порога (0 для бытовых тем,
  2 для граничных, где допустим честный `rag_search`).
- `no_structure` — в ответе нет секции контракта (`## Источники`) и ответ
  короткий (эвристика: ≤ 600 символов).
- `must_redirect` — предложена помощь по профильной теме (проверяется чтением, не regex).

### 1.6. Классы инструментов

Веб-поиск в рантайме доступен не только штатным `web_search`: агент может искать через
маркетплейс-скиллы (Perplexity, GDELT). Поэтому имя `web_search` в полях
`tools_required` / `tools_forbidden` / `rag_before_web` / `max_web_searches` обозначает
**класс web-инструментов**: `web_search` плюс любые `ext_*`-инструменты с `perplexity`,
`gdelt`, `keenable` или `duckduckgo` в имени (актуальный список — константа раннера).
Подтверждено прогонами 2026-08-10: агент отвечал через `web_search` +
`ext_12_r_perplexity_research` + `ext_11_r_gdelt-mcp_discover`, а на rag-001 добавил
`ext_10_r_keenable_search_web_pages` (×4) и `ext_10_r_keenable_fetch_page_content` (×3) —
то есть 9 обращений к вебу при формальном одном вызове `web_search`. Остальные имена в полях датасета (`rag_search`,
`forecast`, `supply_shock`) — конкретные инструменты, без классов.

**Сопоставление имён — только по подстроке.** Инструменты скиллов приходят в событиях
как `ext_<N>_r_<скилл>_<инструмент>`, где `<N>` — порядковый номер загрузки расширения.
Номер не стабилен между перезапусками рантайма: 2026-08-10 в прогоне `003840` под
`ext_11_` был `gdelt-mcp_discover`, а в прогоне `023914` — уже `petro_rag_rag_search`.
Поэтому и класс web-инструментов, и конкретные имена из полей датасета сопоставляются по
вхождению устойчивой части (скилл + инструмент): `rag_search` матчится на
`ext_11_r_petro_rag_rag_search`, `forecast` — на `ext_20_r_oil_price_forecast_forecast`.
Точное равенство и тем более номер использовать нельзя: раннер на равенстве объявит, что
обязательный `rag_search` не вызывался, и `tool_choice` с `forecast_protocol` дадут провал
на исправном ответе.

## 2. Откуда раннер берёт данные (проверено по коду)

| Данные | Источник |
|---|---|
| Постановка вопроса | `POST {APP_URL}/ask` c `question` и **уникальным** `session_id` (`eval-<run_id>-<record_id>`) — иначе история сессии утечёт в контекст следующего вопроса (`app/main.py:97-98`) |
| Статус, стоимость | `GET {APP_URL}/result/{task_id}` → `status`, `cost_usd`, `cost_final`, `reason_code` |
| Сырой текст ответа | `GET {OUROBOROS_URL}/api/tasks/{task_id}` → `result` (markdown целиком), `final_answer` |
| Токены и раунды | там же: плоские поля `prompt_tokens`, `completion_tokens`, `total_rounds`. Поля `usage` у задачи **нет** — проверено на прогоне 2026-08-10 |
| Траектория инструментов | `GET {OUROBOROS_URL}/api/tasks/{task_id}/events?cursor=0&wait=0` → события `type: "tool_call"` с полями `tool`, `args` (аргументы вызова), `result_preview` (обрезан до 2000 символов), `ts`, `is_error` |

Примечания:

- события `tool_call` приходят **задвоенными** (журнал реплеится из двух источников —
  подтверждено smoke-прогоном 2026-08-10): раннер обязан дедуплицировать их по
  `tool_call_id` до подсчёта любых траекторных метрик и телеметрии;
- при заданном `OUROBOROS_NETWORK_PASSWORD` прямые запросы к Ouroboros требуют
  `Authorization: Bearer` (см. `app/ouroboros_client.py:76-79`; `scripts/ask.py` этого пока не делает);
- текстовые проверки — только по `result`; `answer_html` не использовать;
- имена инструментов в событиях: `rag_search`, `web_search`, `forecast`, `supply_shock`.

## 3. Метрики

### 3.1. Детерминированные (уровень fail, если не указано иное)

| Метрика | Формула | Данные | rag | web | hyb | fc | oos |
|---|---|---|---|---|---|---|---|
| `completed` | `status == "completed"`; иначе запись — инфраструктурный сбой, исключается из quality-агрегатов и показывается отдельной строкой | `/result` | ✓ | ✓ | ✓ | ✓ | ✓ |
| `tool_choice` | `set(tools_required) ⊆ called` и `set(tools_forbidden) ∩ called = ∅` | события | ✓ | ✓ | ✓ | ✓ | ✓ |
| `rag_before_web` | `min ts(rag_search) < min ts(первого вызова web-класса)` (если оба вызваны) | события | — | ✓ | ✓ | — | — |
| `web_budget` | `count(вызовов web-класса) ≤ max_web_searches` | события | — | ✓ | ✓ | — | — |
| `citation_format` | все ожидания `expected_citations` выполнены (см. 1.3) | `result` | ✓ | ✓ | ✓ | — | — |
| `citation_validity` | 0 галлюцинированных report-цитат (сверка report+date с `manifest.yaml`); **soft**: страница цитаты встречается в `result_preview` какого-либо вызова `rag_search` (превью обрезано — только warning) | `result` + manifest + события | ✓ | ✓ | ✓ | ✓ | ✓ |
| `fact_accuracy` | все `expected_facts` найдены (см. 1.2) | `result` | ✓ | ✓* | ✓ | — | — |
| `forecast_protocol` | вызов и аргументы соответствуют `forecast_expect`; текстовые must_mention-проверки | события + `result` | — | — | — | ✓ | — |
| `structure` | **warning**: секция `## Источники` присутствует (остальную форму агент выбирает под вопрос) | `result` | ✓ | ✓ | ✓ | ✓ | инверсия |
| `refusal_no_tools` | условия `refusal_expect` (см. 1.5) | события + `result` | — | — | — | — | ✓ |

\* для web-сценария `expected_facts` — только структурный regex «дата среза указана», числа не сверяются.

### 3.2. Телеметрия (не pass/fail; собирается для каждой записи)

| Показатель | Источник |
|---|---|
| `tool_call_counts` | счётчик вызовов **каждого** инструмента (`{"rag_search": 1, "web_search": 2, ...}`) из событий |
| `tokens` | `prompt_tokens` / `completion_tokens` из `GET /api/tasks/{id}` (плюс `total_rounds` — число раундов агента) |
| `duration_sec` | `ts` последнего события − `ts` первого (fallback — wall-clock раннера) |
| `cost_usd` | из `/result`; при `cost_final == false` — доопросить позже или пометить «нижняя граница» |

Агрегаты телеметрии: среднее/медиана/сумма по сценарию и по прогону.

### 3.3. Экспертная оценка

Проверки из 3.1 не читают содержание: ответ может пройти их все и не ответить на
вопрос. Содержательную сторону закрывает поле `judge_criteria` (есть у всех 34 записей),
`reference_answer` (у 14) и `expected_facts`.

Вердикт по каждому критерию выносится **чтением ответа, бинарно**. Автоматический judge
не строится: разметка 34 записей — единицы центов, но модель-судья добавляет свой
недетерминизм поверх агентского, а расползание оценки лечится не пиннингом модели, а
записанными правилами присуждения. Правила, формат вердиктов и журнал уже вынесенных
решений — в `EVAL-RUBRIC.md`; там же зафиксирована базовая линия по прогонам, с которой
сравниваются следующие.

### 3.4. Агрегация

Качество прогона — две независимые метрики по шкале 0–100 %; ни одна не заменяет другую.

**Соответствие протоколу** — по проверкам 3.1. Балл ответа: 0, если провалена блокирующая
проверка (`completed`, `citation_validity`, `fact_accuracy`, `forecast_protocol`,
`refusal_no_tools`); иначе — доля пройденных штрафных (`tool_choice`, `rag_before_web`,
`web_budget`, `citation_format`, `structure`) среди применимых. Метрика прогона — среднее
баллов; `skip` в знаменатель не входит, незавершённая запись получает 0.

**Экспертная оценка** — по 3.3: сумма пройденных `judge_criteria` / сумма всех.

Рядом с ними, не смешиваясь в качество: латентность (средняя `duration_sec`), длина
траектории (среднее число раундов), стоимость ответа (средняя `cost_usd`). Разбивка `tool_call_counts` и доля
галлюцинированных report-цитат — диагностика, а не метрика.

Сравнивать прогоны допустимо только на одинаковом наборе вопросов. Смотреть на **уровень
и тренд** между версиями промпта и моделей, а не на гейт 100 %: агент недетерминирован.
Полные формулы, правила присуждения и формат отчёта — в `EVAL-RUBRIC.md`.

## 4. Протокол прогона

Файлы: `scripts/eval_run.py` (оркестрация; транспорт по образцу `scripts/ask.py` — urllib,
поллинг, Bearer при пароле) и `scripts/eval_agent_checks.py` (чистые функции:
`(record, answer_md, tool_calls, status, manifest) → list[Check]`; без сети).

Шаги на запись: `POST /ask` (уникальный `session_id`) → поллинг `/result` до финала →
`GET /api/tasks/{id}` (сырой `result`, `usage`) → `GET /api/tasks/{id}/events` (разбор
`tool_call`) → детерминированные проверки → дозапись в `eval_runs/<ts>/`.

Выход прогона — три файла: `results.jsonl` (сырой ответ, события, телеметрия, `checks`;
дописывается после каждой записи), `review.md` (документ для экспертной оценки:
вопрос, критерии, эталон, ответ, автопроверки и поля под вердикты; перерисовывается
целиком) и `run_meta.json` (параметры запуска, модели, расход на старте).

CLI: `--dataset`, `--only <id>`, `--scenario <name>`, `--limit`, `--timeout`,
`--budget-usd` (стоп по накопленной стоимости), `--parallel N` (не больше
`OUROBOROS_MODEL_MAX_CONCURRENCY=3` — лишние задачи ждут слот модели, сжигая
собственный дедлайн), `--stall-sec`, `--resume <каталог>`, `--rebuild <каталог>`
(пересчитать телеметрию и проверки без обращения к агенту; затирает `review.md`,
поэтому только до простановки оценок; требует `PYTHONIOENCODING=utf-8`).

Ожидаемая стоимость полного прогона: 34 вопроса × ~$0.05–0.3 ≈ $2–10 (веб-поиск — самая
дорогая часть). Экспертная оценка денег не стоит — она делается чтением.

## 5. Ограничения и известные компромиссы

1. **Недетерминизм агента** — проверяются множества инструментов, а не точные
   последовательности (кроме rag-перед-вебом); допуски на числа. Повтора прогона в раннере
   нет: одна и та же запись гоняется вторым прогоном вручную.
2. **Дрейф веба** — web/hybrid не содержат эталонных чисел; критерии оценки не спрашивают
   «правильное ли число», только дисциплину источников.
3. **`result_preview` обрезан до 2000 символов** — сверка страницы цитаты с выдачей RAG
   только warning; жёсткая ловля выдуманных цитат — по manifest (report+date), этого достаточно.
4. **Приоритет отчётов держится на промпте** (PROBLEMS.md, запись 30) — `rag_before_web`
   и `tool_choice` как раз делают этот инвариант измеримым постфактум.
5. **Граничные out_of_scope** (литий/пшеница/ВИЭ) допускают честный `rag_search`:
   промпт велит «при сомнении считать профильным», и наказывать за проверку базы неверно;
   запрещены только веб-поиск и расчётный модуль.
6. **`cost_final == false`** — стоимость помечается как нижняя граница.
