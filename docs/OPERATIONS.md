# Эксплуатация

Операционная документация: запуск, ключи, устройство, безопасность, обновление.
Краткое описание проекта и обзор возможностей — в [README.md](../README.md).

## Запуск

```bash
git clone --recurse-submodules https://github.com/dertty/petro-market-analyst.git
cd petro-market-analyst
cp .env.example .env      # заполнить OPENROUTER_API_KEY
docker compose up --build
```

Интерфейс — <http://127.0.0.1:8000>. Первая сборка занимает несколько минут: в образ
рантайма ставится расчётный стек (torch CPU, Chronos, statsmodels) и кладутся веса модели
прогнозирования — см. «Расчётный модуль прогнозирования цен».

Скиллы из `skills/` включаются сами — этим занимается сервис `skill-enable`, см. раздел
«Расчётный модуль прогнозирования цен».

Если репозиторий уже склонирован без подмодуля:

```bash
git submodule update --init --recursive
```

## Корпус отраслевых отчётов

`ingest/` собирает файлы отчётов (OPEC, EIA, JODI, санкционные первоисточники и т. д.) в
`data/corpus/` — задел под будущий RAG, без извлечения текста и без подключения к агенту.
Реестр источников — `ingest/registry.yaml`, команды и структура — `ingest/README.md`.

## Расчётный модуль прогнозирования цен

`skills/oil_price_forecast/` — скилл Ouroboros, дающий агенту два инструмента вместо
прикидки в уме:

- **`forecast`** — прогноз спота Brent или WTI на 1/3/6/12 месяцев. Считает двумя
  независимыми методами: **Chronos-Bolt** (предобученная модель, zero-shot) и
  **экспоненциальное сглаживание Хольта** с демпфированным трендом по лог-ценам. Плюс
  случайное блуждание со сносом как бенчмарк. Возвращает медиану и границы интервала
  **80 % (q10–q90)** по каждому методу и готовую интерпретацию с оговорками.
- **`supply_shock`** — диапазон цены при изменении добычи на N млн барр./сутки через
  краткосрочные эластичности спроса и предложения. Возвращает сами эластичности и ссылку
  на работы, откуда взяты их диапазоны.

Исторический ряд — из API EIA (`RBRTE` и `RWTC`), с суточным кэшем. Без ключа модуль
работает на снапшоте из своей поставки и **помечает это в ответе**.

Интервал 80 %, а не привычные 95 %, потому что обученные квантили Chronos-Bolt
заканчиваются на 0.1 и 0.9 — шире пришлось бы экстраполировать, а разные уровни у разных
методов дали бы несопоставимые коридоры.

### Включение

Происходит автоматически. Сервис `skill-enable` из `docker-compose.yml` запускается после
рантайма, проходит по каталогам внутри `skills/` и доводит каждый до рабочего состояния,
после чего завершается. Результат виден в `docker compose logs skill-enable`.

Чтобы скилл заработал, в Ouroboros должны выполниться два условия: вердикт ревью,
привязанный к хешу содержимого, и флаг «включено». Сами собой они не выставляются —
автоматика рантайма при старте штампует вердикт только засеянным native-скиллам
(`telegram`, `unix_computer_use`), и даже там автовключение недоступно всему, что
объявляет разрешение `net`. Внешние скиллы ждут решения владельца.

Скрипт закрывает оба условия штатными owner-эндпоинтами. Дорогое ревью тремя ИИ-моделями
пропускается через owner-аттестацию — «я сам написал этот код и за него ручаюсь». Она
доступна **только для своих** скиллов из `skills/`; встроенные и скачанные с хабов скрипт
не трогает и по правилам рантайма не смог бы. Детерминированные проверки — манифест,
синтаксис, структура — выполняются в любом случае, и при их провале скилл не включится, а
сервис завершится с ненулевым кодом.

**Обратная сторона:** после правки кода скилла перезапуск подтвердит новую версию сам.
Раньше правка требовала осознанного повторного подтверждения человеком. Подробнее —
запись 24 в `PROBLEMS.md`.

Если понадобится сделать то же руками (например, при отключённом сервисе): интерфейс
Ouroboros на <http://127.0.0.1:8766>, вкладка Skills, кнопка пропуска ревью и переключатель.

Расчётный стек (torch CPU, `chronos-forecasting`, statsmodels) стоит в образе рантайма, а
не объявлен зависимостями скилла. Почему именно так и чем за это платим — записи 19–25 в
`PROBLEMS.md`.

### Ручная проверка расчётов

Те же расчёты доступны по HTTP, без агента и без затрат на модель:

```bash
curl "http://127.0.0.1:8766/api/extensions/oil_price_forecast/forecast?benchmark=brent&horizon=3m"
curl "http://127.0.0.1:8766/api/extensions/oil_price_forecast/supply_shock?cut_mbd=2&spot_price=70"
```

Параметры `forecast`: `benchmark` (`brent`/`wti`), `horizon` (`1m`/`3m`/`6m`/`12m`),
`methods` (через запятую). Параметры `supply_shock`: обязательный `cut_mbd`, а также
`spot_price`, `benchmark`, `world_supply_mbd`, `offset_mbd`.

Роуты зовут те же функции, что и инструменты агента, поэтому показывают ровно то, что
увидит агент. Ошибки возвращаются полем `error` с кодом 200 — так же, как у инструментов.

**Только для ручных проверок, не для регулярного опроса.** Первый вызов грузит torch и
веса в процесс сервера: замерено, процесс растёт со 172 до 772 МБ и память не отдаёт.
На время расчёта удерживается глобальный лок расширений в процессе сервера. Прежде чем
вешать на эти роуты что-то автоматическое, нужен кэш результатов — см. `TODO.md`.

## Ключи и настройки

Обязателен один ключ — `OPENROUTER_API_KEY`: модель по умолчанию и обе резервные это
идентификаторы каталога OpenRouter. Второй обязательный параметр, `OUROBOROS_RUNTIME_MODE=light`,
уже стоит в `.env.example`: по умолчанию рантайм работает в режиме `advanced`, где имеет право
писать в собственный репозиторий.

Необязательный — `EIA_API_KEY` для расчётного модуля прогнозирования. Бесплатный, выдаётся
по email сразу: <https://www.eia.gov/opendata/register.php>. Без него модуль не падает, но
считает по снапшоту ряда из своей поставки и помечает это в ответе.

**Ловушка, из-за которой поведение разойдётся между машинами.** У Ouroboros есть свой
веб-интерфейс с настройками. Если сохранить ключ через него, значение запишется в
`data/settings.json` и начнёт **перекрывать** `.env`, а `data/` в git не попадает. Меняйте
ключи только в `.env`.

## Две вещи, которые сбивают с толку

**Папка `data/memory/knowledge` на хосте пустая.** Это точка монтирования: реальные файлы
лежат в `knowledge/` в корне проекта. Туда же смотреть при правках. То же для
`data/skills/external` и `skills/`.

**Рантайм виден на порту 8766, а не 8765.** Так сделано, чтобы не конфликтовать с нативной
установкой Ouroboros, если она работает на той же машине. Внутри сети Docker порт всегда 8765,
приложение от этого не зависит. Меняется через `OUROBOROS_HOST_PORT` в `.env`.

## Как это работает

Каждый вопрос — отдельная задача рантайма с собственным каталогом данных
(`memory_mode: "forked"`). Поэтому между вкладками и пользователями не течёт ни история, ни
память: у задачи пустой журнал переписки и своя копия базы знаний.

Историю сессии несёт приложение: идентификатор сессии живёт в `sessionStorage` браузера, и при
каждом новом вопросе предыдущие вопросы и ответы этой сессии подставляются в текст задачи.
Отсюда два следствия:

- **Перезагрузка страницы начинает новую сессию.** Прошлые ответы остаются в рантайме, но связь
  с ними теряется — это осознанный выбор в пользу изоляции.
- **Каждый следующий вопрос в сессии дороже предыдущего**, потому что история едет целиком.

## Правка базы знаний

`knowledge/` — обычные markdown-файлы под git. В контекст задачи попадает только
`index-full.md`; остальные топики агент читает сам, когда они нужны. Поэтому:

- новый топик — новый файл в `knowledge/`, **плоско**: вложенные каталоги в индекс не попадают;
- добавили топик — допишите строку про него в `index-full.md`, иначе агент о нём не узнает;
- правки подхватываются без пересборки образа, каталог смонтирован.

Инструмент записи знаний у задачи отключён намеренно: на своём каталоге задачи запись не попала
бы в общую базу, а инструмент отрапортовал бы успехом. База меняется только вами и только
через git.

## Безопасность

Аналитической задаче запрещено править код: снят большой список инструментов
(`app/ouroboros_client.py`, `DISABLED_TOOLS`) и объявлены защищёнными каталоги `skills`,
`vendor`, `app`. Python для расчётов при этом оставлен.

**При обновлении подмодуля список инструментов надо пересматривать.** Белого списка в контракте
задачи нет, только чёрный, а неизвестное имя молча ничего не отключает: новый инструмент записи
в новой версии Ouroboros ослабит защиту без единого признака.

Порт рантайма привязан к `127.0.0.1`. Выносить его в сеть без `OUROBOROS_NETWORK_PASSWORD`
нельзя: при пустом пароле проверка пропускает всех. У самого приложения аутентификации нет
вовсе — см. `PROBLEMS.md`.

## Обновление рантайма

```bash
cd vendor/ouroboros
git fetch managed --tags
git checkout <новый тег>
cd ../..
git add vendor/ouroboros && git commit -m "Ouroboros <новый тег>"
```

`origin` подмодуля — ваш форк (туда уходят коммиты), `managed` — оригинальный репозиторий
(оттуда приходят обновления).

Если после клонирования на Windows контейнерный git показывает весь `vendor/ouroboros`
изменённым, это перевод строк:

```bash
cd vendor/ouroboros
git config core.autocrlf false && git config core.eol lf
git rm --cached -r . && git reset --hard
```
