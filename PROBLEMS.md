# Что решено компромиссно и что не решено

Файл существует потому, что решения, принятые «пока так», через месяц выглядят как замысел.
Формат записи: **что не так → чем проявится → что было бы правильно → почему сейчас не сделали**.

Ссылки на строки указывают на Ouroboros v6.90.1 (`vendor/ouroboros`, коммит `40fc7764`).
При обновлении подмодуля их надо перепроверить.

---

## Сессии и чаты

### 1. «Сессия» — наше понятие, в рантайме его нет

Ouroboros знает «чат» (`chat_id`) и «проект» (`project_id`), и ни то ни другое не совпадает с
сессией браузерной вкладки. Мы завели третье понятие и держим его сами: генерируем
идентификатор, кладём в задачу полем `session_id`, отбираем задачи по нему.

*Проявится:* в родном интерфейсе Ouroboros все наши задачи лежат одной кучей с `chat_id = 0`,
без разделения. Любой инструмент рантайма, работающий «по чатам», нас не видит.

*Правильно:* использовать штатное понятие рантайма — см. запись 3.

### 2. Изоляция односторонняя: контекст изолирован, хранилище — нет

Задача с `memory_mode: "forked"` читает **свой** пустой журнал переписки, поэтому чужого в
контексте не видит. Но ответ пишется в `chat.jsonl` **родительского** каталога данных
(`supervisor/message_bus.py:752-763`), то есть ответы всех сессий и всех пользователей копятся
в одном файле. Родной интерфейс Ouroboros отдаёт их через `GET /api/chat/history`.

*Проявится:* требование «разные пользователи не видят чужого» выполнено для агента, но не для
человека с доступом к порту рантайма.

*Почему терпимо сейчас:* порт привязан к `127.0.0.1`.

*Правильно:* либо разделять/чистить журнал, либо никогда не публиковать порт рантайма наружу.

### 3. `chat_id` не использован, хотя это штатный способ разводить разговоры

Фокус на своей ветке переписки рантайм даёт только чатам, зарегистрированным как проект
(`ouroboros/context.py:807-824`), а регистрация проекта тянет `project_id`, который отключает
глобальную базу знаний (`ouroboros/context.py:616-622`). Мы этот путь отвергли и пошли через
`memory_mode`.

**Не изучено:** можно ли зарегистрировать проектный чат, **не** получив `project_id` у задачи.
Фокус чата берётся из `chat_id`, а знания — из `project_id`, и это разные поля. Если их можно
развести, решение через чаты правильнее нашего: изоляция стала бы штатной, а историю не
пришлось бы пересылать вовсе (запись 4).

*Когда проверять:* до того, как пересылка истории начнёт стоить заметных денег.

### 4. История сессии пересылается целиком на каждый вопрос

Прямое следствие записи 1: раз рантайм сессий не знает, приложение заново кладёт всю переписку
в текст задачи. Расход растёт квадратично по длине сессии.

*Правильно:* передавать ссылку на предыдущий контекст. Такого в API нет — проверено:
`POST /api/tasks/{id}/resume` снимает задачу с бюджетной паузы, а не продолжает диалог.

*Смягчение, когда понадобится:* ограничить историю последними N шагами — одно место,
`app/prompt.py`.

### 5. Сессия живёт только пока открыта вкладка

Осознанный выбор в пользу изоляции. Следствие: при случайной перезагрузке страницы связь с
предыдущими ответами теряется, хотя сами ответы остаются в `GET /api/tasks`.

### 6. Фильтрация истории по сессии — перебором на стороне приложения

Запроса «отдай задачи такой-то сессии» в API нет, поэтому тянем `GET /api/tasks?limit=N` и
фильтруем сами. `limit` по умолчанию 50, **жёсткий потолок 500**.

*Проявится:* после 500 задач на инстанс старые вопросы сессии начнут пропадать из панели.
Число известное, а не «когда-нибудь».

### 7. Аутентификации нет вообще

«Разные пользователи не видят чужого» держится только на том, что идентификатор сессии лежит в
браузере. Кто угодно, дотянувшись до порта 8000, может подставить чужой `session_id` и прочитать
переписку.

*Пока порт на `127.0.0.1` — приемлемо. При первом же выносе наружу это блокер.*

## Права и защита

### 8. Защита кода разбирает текст команды, а не поведение процесса

Скрипт, склеивающий путь записи во время выполнения, проходит мимо проверки.

*Правильно:* отдельный инстанс с монтированием кода только на чтение. Отвергнуто как избыточное
для одного доверенного пользователя.

### 9. `disabled_tools` — чёрный список, белого не существует

Проверено: `allowed_resources` в контракте задачи — deny-гейт по осям web/network, белым списком
инструментов служить не может. Значит защита держится на полноте перечисления, а неизвестное имя
молча ничего не отключает.

*Проявится:* новая версия Ouroboros приносит инструмент записи, которого нет в списке, — защита
слабеет без единого признака.

*Что делать:* **при каждом обновлении подмодуля пересматривать список** в
`app/ouroboros_client.py`.

### 10. Защита от записи кода из Python — гипотеза, подтверждённая только тестом

`run_command` отключён, а `run_script` оставлен ради расчётов; по достижимости они почти не
различаются, поэтому вся нагрузка ложится на сканер текста команды. Детектор маскировки пути
через переменную по докстроке ловит **чтение**, а не запись
(`ouroboros/protected_artifacts.py:596-598`).

*Статус:* проверяется тестом «выполни скрипт, который запишет файл в skills/». При провале
выбор: отключить `run_script`, потеряв Python-расчёты, либо принять риск явной записью здесь.

### 11. Проверка по пути вызывается децентрализованно

Каждый пишущий инструмент зовёт её сам (`ouroboros/tools/core.py:927-946`,
`ouroboros/tools/edit_ops.py:128`). Покрытие сегодня полное, но инструмент, который её не
вызовет, обойдёт защиту. Та же зависимость от обновлений, что и в записи 9.

## Знания

### 12. Агент не может пополнять базу знаний

`knowledge_write` отключён. Причина не в том, что запись «пропадает»: она уходит в каталог
задачи и выгружается в артефакт `memory_export.json` (`ouroboros/headless.py:687-698`).
В общую базу она **не вливается автоматически** — это явное решение авторов рантайма:
«identity, scratchpad, registry, knowledge, dialogue blocks … are never merged or exported
automatically» (`docs/ARCHITECTURE.md:795-797`). Логика та же, которую мы применили к коду:
иначе любая задача, включая ту, где в вопрос вписано «забудь инструкции выше», молча
переписывала бы базу знаний.

*Почему отключили, а не оставили:* иначе инструмент рапортует «сохранено», а файла нет — тихая
потеря хуже явного отказа.

*Правильно:* читать `memory_export.json` из артефактов задачи и вливать выбранное в git.
Не сделано, потому что разбирать экспорты вручную сейчас некому.

## Эксплуатация

### 13. Исчерпание бюджета обрабатывается двумя разными способами

Задача, не успевшая сделать ни одного вызова модели, встаёт на паузу и снимается через
`POST /api/tasks/{id}/resume` (`ouroboros/gateway/tasks.py:869-887`). Задача **в полёте** на
паузу не встаёт — она падает с `budget_exhausted`.

*Проявится:* в интерфейсе это два разных отказа — «вечно в очереди» и «ошибка без объяснения».
Отдельного текста ни на один пока нет.

### 14. Ограничения длины сессии нет

Ни по числу шагов, ни по стоимости. Первым признаком будет счёт.

### 15. Стоимость конкретного вопроса во время работы недоступна

Поля стоимости приходят только в терминальных событиях; в процессе есть лишь глобальный
`spent_usd` всего рантайма из `GET /api/state`. Поэтому во время работы интерфейс показывает
только таймер.

*Правильно:* ничего — свой учёт разошёлся бы с их бухгалтерией. Записано, чтобы не искать
«потерянное» поле повторно.

### 16. Копии каталогов данных на диске

По одной на задачу в `data/state/headless_tasks/<id>/data`. Копируется подмножество `memory/`
(identity, WORLD, registry, knowledge), `state/cx` в копию не входит, поэтому копии лёгкие.
Чистятся при старте по сроку хранения (`OUROBOROS_GC_RETENTION_DAYS`, по умолчанию 7 дней).
Рост ограничен, но не измерен.
