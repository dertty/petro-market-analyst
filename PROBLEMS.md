# Что решено компромиссно и что не решено

Файл существует потому, что решения, принятые «пока так», через месяц выглядят как замысел.
Формат записи: **что не так → чем проявится → что было бы правильно → почему сейчас не сделали**.

Ссылки на строки указывают на Ouroboros v6.90.1 (`vendor/ouroboros`, коммит `40fc7764`).
При обновлении подмодуля их надо перепроверить.

---

## Сессии и чаты

### 1. «Сессия» — наше понятие, в рантайме его нет

Ouroboros знает «чат» (`chat_id`) и «проект» (`project_id`), и ни то ни другое не совпадает с
сессией браузерной вкладки. Мы завели третье понятие и держим его сами: генерируем
идентификатор, кладём в задачу полем `session_id`, отбираем задачи по нему.

*Проявится:* в родном интерфейсе Ouroboros все наши задачи лежат одной кучей с `chat_id = 0`,
без разделения. Любой инструмент рантайма, работающий «по чатам», нас не видит.

*Правильно:* использовать штатное понятие рантайма — см. запись 3.

### 2. Изоляция односторонняя: контекст изолирован, хранилище — нет

Задача с `memory_mode: "forked"` читает **свой** пустой журнал переписки, поэтому чужого в
контексте не видит. Но ответ пишется в `chat.jsonl` **родительского** каталога данных
(`supervisor/message_bus.py:752-763`), то есть ответы всех сессий и всех пользователей копятся
в одном файле. Родной интерфейс Ouroboros отдаёт их через `GET /api/chat/history`.

*Проявится:* требование «разные пользователи не видят чужого» выполнено для агента, но не для
человека с доступом к порту рантайма.

*Почему терпимо сейчас:* порт привязан к `127.0.0.1`.

*Правильно:* либо разделять/чистить журнал, либо никогда не публиковать порт рантайма наружу.

### 3. `chat_id` не использован, хотя это штатный способ разводить разговоры

Фокус на своей ветке переписки рантайм даёт только чатам, зарегистрированным как проект
(`ouroboros/context.py:807-824`), а регистрация проекта тянет `project_id`, который отключает
глобальную базу знаний (`ouroboros/context.py:616-622`). Мы этот путь отвергли и пошли через
`memory_mode`.

**Не изучено:** можно ли зарегистрировать проектный чат, **не** получив `project_id` у задачи.
Фокус чата берётся из `chat_id`, а знания — из `project_id`, и это разные поля. Если их можно
развести, решение через чаты правильнее нашего: изоляция стала бы штатной, а историю не
пришлось бы пересылать вовсе (запись 4).

*Когда проверять:* до того, как пересылка истории начнёт стоить заметных денег.

### 4. История сессии пересылается целиком на каждый вопрос

Прямое следствие записи 1: раз рантайм сессий не знает, приложение заново кладёт всю переписку
в текст задачи. Расход растёт квадратично по длине сессии.

*Правильно:* передавать ссылку на предыдущий контекст. Такого в API нет — проверено:
`POST /api/tasks/{id}/resume` снимает задачу с бюджетной паузы, а не продолжает диалог.

*Смягчение, когда понадобится:* ограничить историю последними N шагами — одно место,
`app/prompt.py`.

### 5. Сессия живёт только пока открыта вкладка

Осознанный выбор в пользу изоляции. Следствие: при случайной перезагрузке страницы связь с
предыдущими ответами теряется, хотя сами ответы остаются в `GET /api/tasks`.

### 6. Фильтрация истории по сессии — перебором на стороне приложения

Запроса «отдай задачи такой-то сессии» в API нет, поэтому тянем `GET /api/tasks?limit=N` и
фильтруем сами. `limit` по умолчанию 50, **жёсткий потолок 500**.

*Проявится:* после 500 задач на инстанс старые вопросы сессии начнут пропадать из панели.
Число известное, а не «когда-нибудь».

### 7. Аутентификации нет вообще

«Разные пользователи не видят чужого» держится только на том, что идентификатор сессии лежит в
браузере. Кто угодно, дотянувшись до порта 8000, может подставить чужой `session_id` и прочитать
переписку.

*Пока порт на `127.0.0.1` — приемлемо. При первом же выносе наружу это блокер.*

## Права и защита

### 8. Защита кода разбирает текст команды, а не поведение процесса

Скрипт, склеивающий путь записи во время выполнения, проходит мимо проверки.

*Правильно:* отдельный инстанс с монтированием кода только на чтение. Отвергнуто как избыточное
для одного доверенного пользователя.

### 9. `disabled_tools` — чёрный список, белого не существует

Проверено: `allowed_resources` в контракте задачи — deny-гейт по осям web/network, белым списком
инструментов служить не может. Значит защита держится на полноте перечисления, а неизвестное имя
молча ничего не отключает.

*Проявится:* новая версия Ouroboros приносит инструмент записи, которого нет в списке, — защита
слабеет без единого признака.

*Что делать:* **при каждом обновлении подмодуля пересматривать список** в
`app/ouroboros_client.py`.

### 10. Защита от записи кода из Python — гипотеза, подтверждённая только тестом

`run_command` отключён, а `run_script` оставлен ради расчётов; по достижимости они почти не
различаются, поэтому вся нагрузка ложится на сканер текста команды. Детектор маскировки пути
через переменную по докстроке ловит **чтение**, а не запись
(`ouroboros/protected_artifacts.py:596-598`).

*Статус:* проверяется тестом «выполни скрипт, который запишет файл в skills/». При провале
выбор: отключить `run_script`, потеряв Python-расчёты, либо принять риск явной записью здесь.

### 11. Проверка по пути вызывается децентрализованно

Каждый пишущий инструмент зовёт её сам (`ouroboros/tools/core.py:927-946`,
`ouroboros/tools/edit_ops.py:128`). Покрытие сегодня полное, но инструмент, который её не
вызовет, обойдёт защиту. Та же зависимость от обновлений, что и в записи 9.

## Знания

### 12. Агент не может пополнять базу знаний своим инструментом

`knowledge_write` отключён. Причина не в том, что запись «пропадает»: она уходит в каталог
задачи и выгружается в артефакт `memory_export.json` (`ouroboros/headless.py:687-698`).
В общую базу она **не вливается автоматически** — это явное решение авторов рантайма:
«identity, scratchpad, registry, knowledge, dialogue blocks … are never merged or exported
automatically» (`docs/ARCHITECTURE.md:795-797`). Логика та же, которую мы применили к коду:
иначе любая задача, включая ту, где в вопрос вписано «забудь инструкции выше», молча
переписывала бы базу знаний.

*Почему отключили, а не оставили:* иначе инструмент рапортует «сохранено», а файла нет — тихая
потеря хуже явного отказа.

*Но один канал в общую базу всё же пишет — не инструментом, а пост-обработкой задачи.*
Финализатор зовёт её с родительским диском, чтобы выводы не пропали вместе с дочерним
(`ouroboros/agent_task_pipeline.py:133-177`), и через него проходят две вещи:
номинации в `improvement-backlog.md` (`append_backlog_items`) и `memory_actions` из
experience review, создающие новые топики знаний (`apply_memory_actions`). У нас
`knowledge/` примонтирован в канонический диск (`docker-compose.yml:13`), поэтому такие
записи сразу видны в `git status` — так появился топик `source_fallbacks` и строка о нём
в `index-full.md`, а у элемента `ibl-a2fbf1ddc1de` вырос `count`.

Ограничение записи 12 остаётся в силе: свободную запись знаний агентом (`knowledge_write`)
рантайм не пропускает, а этот канал узкий — только то, что модель номинировала в разборе
задачи по фиксированной схеме.

*Правильно:* ревьюить перед коммитом то, что приехало само, и читать `memory_export.json`
из артефактов задачи для остального. Не сделано, потому что разбирать экспорты вручную
сейчас некому.

## Эксплуатация

### 13. Исчерпание бюджета обрабатывается двумя разными способами

Задача, не успевшая сделать ни одного вызова модели, встаёт на паузу и снимается через
`POST /api/tasks/{id}/resume` (`ouroboros/gateway/tasks.py:869-887`). Задача **в полёте** на
паузу не встаёт — она падает с `budget_exhausted`.

*Проявится:* в интерфейсе это два разных отказа — «вечно в очереди» и «ошибка без объяснения».
Отдельного текста ни на один пока нет.

### 14. Ограничения длины сессии нет

Ни по числу шагов, ни по стоимости. Первым признаком будет счёт.

### 15. Стоимость конкретного вопроса во время работы недоступна

Поля стоимости приходят только в терминальных событиях; в процессе есть лишь глобальный
`spent_usd` всего рантайма из `GET /api/state`. Поэтому во время работы интерфейс показывает
только таймер.

*Правильно:* ничего — свой учёт разошёлся бы с их бухгалтерией. Записано, чтобы не искать
«потерянное» поле повторно.

### 16. Копии каталогов данных на диске

По одной на задачу в `data/state/headless_tasks/<id>/data`. Копируется подмножество `memory/`
(identity, WORLD, registry, knowledge), `state/cx` в копию не входит, поэтому копии лёгкие.
Чистятся при старте по сроку хранения (`OUROBOROS_GC_RETENTION_DAYS`, по умолчанию 7 дней).
Рост ограничен, но не измерен.

### 30. Перезапуск во время ревью скилла блокирует этот скилл на два часа

Воспроизведено 2026-08-09. Рантайм штатно перезапустил себя, пока шла проверка
`oil_price_forecast`. Процесс умер на середине и оставил
`data/state/skills/<скилл>/review_job.json` со `status: running`. После этого **любая**
попытка ревью или owner-аттестации этого скилла падает с HTTP 500 и
`RuntimeError: another process still owns this skill review lifecycle`
(`ouroboros/skill_review_runner.py:769`), а расширение не грузится — роуты отдают 409
`review_stale`.

Уборка таких маркеров у рантайма есть (`reconcile_stale_review_jobs`), но снимает маркер
только если процесс-владелец мёртв **или** сердцебиение старше порога
(`mark_stale_review_job_interrupted`, там же:339-344). Обе проверки здесь дают осечку:

- в маркере записан `pid: 7`, и перезапущенный контейнер поднимает сервер **снова с PID 7** —
  проверка «владелец жив» даёт ложное «да»;
- порог `OUROBOROS_SKILL_REVIEW_JOB_STALE_SEC` по умолчанию **7200 секунд**.

*Проявится:* скилл выпадает из набора инструментов задачи на два часа, а `skill-enable`
честно отработает, но сообщит, что включить не смог. В логах при этом ни одной ошибки
приложения — только 500 на эндпоинте аттестации.

*Что сделано:* порог опущен до 300 секунд переменной в `docker-compose.yml`. Живая проверка
обновляет сердцебиение каждые 30 секунд (`_HEARTBEAT_INTERVAL_SEC`), так что запас
десятикратный — настоящую долгую проверку это не прервёт, а застрявший маркер уберётся за
пять минут вместо двух часов.

*Правильно:* сверять не только PID, но и время старта процесса — тогда переиспользование
PID после перезапуска перестало бы обманывать проверку. Это правка рантайма, а не наша.

*Если уже застряло:* удалить `data/state/skills/<скилл>/review_job.json`. Файл разовый,
лежит под `data/`, вне git, создаётся заново.

### 31. Одно действие в веб-интерфейсе замораживает весь конфиг на вендорских дефолтах

Окружение и `data/settings.json` — не два слоя с приоритетом, а один канал с защёлкой:
значение из окружения применяется **только к ключам, которых в файле нет или значение
пусто** (`ouroboros/config.py:1336-1347`). Как только ключ появился в файле, `.env` по нему
мёртв.

А появляются они там все разом. Owner-эндпоинты настроек делают read-modify-write через
`_owner_read_settings_raw()` (`ouroboros/gateway/settings.py:395-404`), а тот сливает
эталонные дефолты с файлом и **окружение не смотрит вовсе**; затем `_owner_write_settings`
пишет на диск все полторы сотни ключей. То есть переписывает конфиг целиком не только
сохранение ключа через тот интерфейс, о котором предупреждает `.env.example`, а любое
действие в нём.

Воспроизведено 2026-08-09. В `data/logs/events.jsonl` запись
`{"ts": "…T17:26:57", "type": "owner_api_action", "action": "context_mode",
"context_mode": "low", "previous_context_mode": "max"}` — одно переключение контекста
Max → Low. Файла до этого не было; после появился со 134 ключами на дефолтах, и конфиг
разошёлся с `.env` по пяти позициям: `OUROBOROS_MODEL` стал `x-ai/grok-4.5` вместо terra,
`OUROBOROS_WEBSEARCH_MODEL` — `gpt-5.2` вместо luna, в судьи вернулся
`anthropic/claude-sonnet-5`, убранный как в 11 раз дороже (запись в `.env.example`),
`OUROBOROS_RUNTIME_MODE` — `advanced` вместо `light`, `OUROBOROS_SERVER_HOST` —
`127.0.0.1` вместо `0.0.0.0`.

*Проявится:* молча и только счётом. `.env` выглядит настроенным, в git лежат нужные
значения, расхождение не логируется и ни в одном ответе API не видно. По слоту поиска
это разница между $0.20/$0.60 и $1.75/$14 за миллион токенов.

*Что сделано (переделано 2026-08-10):* `scripts/seed_settings.py` и одноразовый сервис
`settings-seed` в `docker-compose.yml` — **записывает** наши значения в файл строго до
старта рантайма. Первая версия скрипта поступала наоборот: снимала ключи из файла, чтобы
их авторствовало окружение. Это оказалось хрупкой стороной сделки, потому что
`_owner_read_settings_raw()` сливает дефолты с файлом как `merged = dict(defaults);
merged.update(файл)` — то есть **значение из файла перезапись из интерфейса переживает**,
а жившее только в окружении заменяется вендорским дефолтом. Источником истины остаётся
`.env` (он документирован и попадает в git через `.env.example`), а seed проецирует его
на диск. Окружение сервису отдаётся YAML-якорем от блока рантайма, а не копией списка.

*Что это дало сверх устойчивости:* через тот же канал задаётся `OUROBOROS_CONTEXT_MODE:
low`. Это один из трёх ключей, которые рантайм объявил owner-защёлками, авторуемыми
только с диска (`config._DISK_AUTHORED_SETTINGS`; окружение их не задаёт по замыслу
авторов, `config.py:1338`). Вендорский дефолт по нему — `max`, и до этой правки наш `low`
жил только в незакоммиченном файле: потеря файла молча возвращала `max` вместе со счётом.
Два других ключа — `OUROBOROS_CONTEXT_MODE_AUTO_LOW` и `OUROBOROS_SAFETY_MODE` — скрипт
намеренно не трогает: у первого есть рантаймовая защёлка против очистки, второй про
безопасность, и оба должны оставаться решением человека.

*Чего это по-прежнему не закрывает:* сохранение из интерфейса всё так же переписывает
файл целиком, и ключи, которых нет в списке скрипта, всё так же уедут на вендорские
дефолты. Список в `PROJECTED_FROM_ENV` надо пополнять вместе с `docker-compose.yml`.

*Правильно:* чтобы owner-эндпоинты читали текущее состояние через `load_settings()`, где
окружение участвует, а не через `_owner_read_settings_raw()`. Это правка форка рантайма,
а не наша, и до неё единственная надёжная дисциплина — не трогать настройки в веб-интерфейсе
Ouroboros.

### 32. Резервная модель того же семейства убивает задачу: reasoning у OpenAI шифрованный

Воспроизведено 2026-08-09 на вопросе `rag-002` через `scripts/ask.py`. Задача
`2ff6869418914fb3` шла 151 секунду, потратила $0.9977 и упала со `status: failed`,
`reason_code: provider_unavailable`. Ответа человек не получил.

OpenAI отдаёт рассуждения не текстом, а зашифрованным блоком (`rs_...`), привязанным к
конкретной модели. Санитайзер, который срезает такие блоки при переключении моделей,
сравнивает **семейство** — часть идентификатора до `/` (`_model_family`,
`ouroboros/llm.py:1785`) — и при совпадении возвращает историю нетронутой
(`sanitize_reasoning_on_model_switch`, там же:1907-1922). Для подписей Anthropic это верно,
для шифрованных блоков OpenAI — нет.

Дальше сходятся три обстоятельства. `OUROBOROS_MODEL_FALLBACKS` в `.env` не задан, поэтому
действует вендорский дефолт `openai/gpt-5.6-luna` (`ouroboros/config.py:101`). Основная
модель — `openai/gpt-5.6-terra`. Семейство у них одно, значит на транзиентном сбое terra
цепочка фолбэка (`ouroboros/loop.py:2517`, вызов санитайзера — там же:2556) отправляет блоки
terra в luna. В `data/logs/progress.jsonl` это видно строкой
`⚡ Fallback: openai/gpt-5.6-terra → openai/gpt-5.6-luna`, а в `data/logs/chat.jsonl` — ответом
провайдера: `Error code: 404 — Your request contains encrypted reasoning or compaction content
that was produced under a different model. Encrypted payloads can only be replayed to the
endpoint...`. Цепочка из одного элемента на этом исчерпана — `loop.py:3286`.

Парадокс, который стоит запомнить: фолбэк **внутри** семейства openai ломается, а фолбэк
наружу работает. У модели другого семейства санитайзер сработал бы и вырезал блоки.

Оба штатных предохранителя промахиваются мимо этой ошибки по гейтам, а не по существу:
`_openrouter_signature_retry_kwargs` (`llm.py:1814-1831`) требует статус 400, здесь 404;
`_strip_kwargs_for_encrypted_body_error` (там же:1997-2039) требует и код 400, и подстроку
`"encrypted content"` в тексте — а в тексте `"encrypted reasoning or compaction content"`,
такой подстроки в нём нет. Сам файл ниже (`llm.py:1877-1886`) уже знает, что шифрованные
блоки OpenAI не переносимы, но эта поправка применена только к смене эндпоинта одной и той же
модели и до санитайзера смены модели не дошла.

*Проявится:* редко и дорого — только когда у основной модели случился транзиентный сбой,
то есть в момент, ради которого фолбэк и заведён. Пользователь видит отказ без объяснения,
деньги за пройденную часть задачи списаны.

*Правильно:* в `sanitize_reasoning_on_model_switch` сравнивать для `openai/*` полный
идентификатор модели, а не семейство, и расширить гейт `_strip_kwargs_for_encrypted_body_error`
на 404 и на формулировку `"encrypted reasoning ... content"`. Это правка форка рантайма,
а не наша.

*Что сделано:* кросс-модельный фолбэк выключен — `OUROBOROS_MODEL_FALLBACKS` в `.env`
задан **равным** `OUROBOROS_MODEL`. Активная модель выбрасывается из цепочки
(`get_fallback_models`, `config.py:400-410`), и цепочка схлопывается в пустую; это штатный
приём, которым пользуются бенчмарки рантайма. Резервирование провайдеров внутри одной
модели у OpenRouter при этом сохраняется, а оно и закрывает большую часть транзиентных
сбоев. Плата за это — при настоящем отказе terra задача честно падает вместо того, чтобы
дописаться другой моделью.

*Чем это далось дороже одной строки:* отключить фолбэк пустым значением нельзя, и мимо
этого легко пройти. Пустую переменную окружения рантайм пропускает и оставляет вендорский
дефолт (`config.py:1343-1344`; исключение сделано единственному ключу
`OUROBOROS_RETURN_REASONING`) — то есть `OUROBOROS_MODEL_FALLBACKS=` вернуло бы ровно ту же
поломку, выглядя при этом как её починка. Сверх того ключа не было в блоке `environment:`
`docker-compose.yml`, то есть в контейнер он не попадал вовсе, и он лежал в
`data/settings.json`, где по записи 31 окружение по нему мертво. Поэтому правка вышла на
четыре файла: значение в `.env` и `.env.example`, проброс в `docker-compose.yml` и ключ в
списке seed-скрипта (`PROJECTED_FROM_ENV` в `scripts/seed_settings.py` — на момент правки
скрипт назывался иначе и снимал ключи вместо записи, см. запись 31).

## Расчётный модуль прогнозирования (skills/oil_price_forecast/)

### 19. Расчётный стек стоит в образе рантайма, а не в изоляции скилла

Штатный путь — `dependencies` в манифесте и установка в `.ouroboros_env` скилла. Он здесь
не работает по двум независимым причинам, обе проверены по исходникам v6.90.1.

Первая: CPU-сборку torch туда не поставить. Имя пакета проходит фильтр, где символ `+`
запрещён явно (`ouroboros/marketplace/install_specs.py:56`), поэтому `torch==X+cpu` не
пройдёт, а задать `--index-url` негде — argv pip фиксирован
(`ouroboros/marketplace/isolated_deps.py:173`), а `PIP_INDEX_URL`/`PIP_EXTRA_INDEX_URL`
вырезаются из окружения установщика (`isolated_deps.py:27-30`). Голый `torch` с PyPI на
linux/x86_64 тянет CUDA-сборку с пачкой `nvidia-*` при таймауте pip 600 с.

Вторая: само наличие изолированных зависимостей включает out-of-process-диспатч
(`ouroboros/extension_process_runner.py:170-173`), где на каждый вызов инструмента
поднимается новый интерпретатор и `register()` выполняется заново. Веса Chronos
перечитывались бы с диска при каждом вызове.

*Проявится:* образ рантайма тяжелее примерно на 1,4 ГБ — измерено по слоям: torch с
chronos и statsmodels занимают 1,22 ГБ, веса Chronos-Bolt ещё 191 МБ. Первый вызов `forecast` после
старта рантайма занимает около 18 с против ~1 с у последующих: импорт torch и чтение весов
происходят лениво, при первом обращении. В таймаут инструмента (180 с) укладывается с
запасом, но первый вопрос про прогноз ощутимо дольше остальных. Падение torch (нативный segfault)
роняет `server.py` целиком, а не только вызов инструмента. Каждый вызов расширения
удерживает глобальный лок расширений на всё время работы, так что второй запрос ждёт.

*Правильно:* `companion_process` — долгоживущий процесс под надзором хоста держит модель
загруженной, инструмент остаётся тонким клиентом. Изоляция от падений сохраняется.

*Почему сейчас не сделали:* заметно больший скоуп — свой IPC, свой жизненный цикл, своя
отладка, — а torch всё равно пришлось бы ставить через тот же Dockerfile. Для одного
пользователя с одним запросом за раз лок и риск падения приемлемы.

### 20. `EIA_API_KEY` идёт мимо механизма Settings и grant'ов

Ключ пробрасывается через `docker-compose.yml` и читается из `os.environ`. Штатный путь —
`env_from_settings` плюс `api.get_settings()` — требует, чтобы ключ лежал в
`data/settings.json`: переменная окружения его туда не засеет, потому что окружение
перекрывает только ключи из `SETTINGS_DEFAULTS` (`ouroboros/config.py:1336-1347`).
А как только ключ там появится, он классифицируется как `custom_secret` и требует явного
owner-grant, привязанного к хешу содержимого скилла (`ouroboros/skill_loader.py:586-606`).

*Проявится:* ключ не виден в интерфейсе настроек Ouroboros и не участвует в его модели
разрешений. Скилл получает его в обход этого механизма.

*Почему так:* grant привязан к хешу, и **любая правка кода скилла его сбрасывает** —
скилл переставал бы получать ключ после каждого изменения, молча уходя на снапшот.
Для ключа, который не является секретом в сильном смысле (бесплатный, выдаётся по email,
даёт только чтение публичных рядов), цена такой дисциплины выше пользы.

### 21. Снапшот ряда протухает, и это видно только в поле ответа

`skills/oil_price_forecast/data/*_weekly.csv` снят 2026-08-09. Когда API EIA недоступен
или ключ не задан, прогноз считается на нём, а `origin` в ответе становится `snapshot` и
интерпретация несёт предупреждение.

*Проявится:* если агент проигнорирует предупреждение, старая цена уедет в отчёт как
текущая. Защита здесь только текстовая.

*Правильно:* при `origin == "snapshot"` и возрасте ряда больше месяца отказываться считать
вовсе. Не сделано: отказ на пустом месте хуже, чем помеченный ответ, а порог «месяц»
пришлось бы выдумывать.

### 22. Эластичности в `supply_shock` взяты из литературы, а не оценены на данных

Диапазоны |η_d| = 0,02…0,10 и η_s = 0,02…0,12 зашиты константами со ссылкой на Hamilton
(2009), Baumeister & Peersman (2013), Caldara, Cavallo & Iacoviello (2019). Модель —
сравнительная статика без динамики: она говорит, где установится цена, но не за сколько
недель. Запасы и стратегические резервы гасят шок и в формуле не учтены; при больших
выпадениях линейное приближение завышает эффект.

*Проявится:* число выглядит точнее, чем оно есть. Поэтому инструмент возвращает сами
эластичности и их источник, а `knowledge/method.md` требует их цитировать.

*Правильно:* оценивать эластичности на данных (SVAR по Kilian). Это отдельная работа
масштаба всего остального модуля, и её результат всё равно был бы диапазоном.

### 23. Прогноз строится по споту, а рынок торгует фьючерс

Ряды EIA `RBRTE` и `RWTC` — спотовые котировки, публикуются с лагом около недели.
Фьючерсная кривая, по которой рынок реально формирует ожидания, в модуле не участвует.

*Проявится:* последнее наблюдение может расходиться с сегодняшней котировкой на дневное
движение и больше; в контанго или бэквордации прогноз по споту систематически расходится
с тем, что заложено в кривой.

*Правильно:* добавить фьючерсную кривую отдельным источником и сравнивать с ней прогноз —
расхождение модели с кривой само по себе содержательно. Не сделано: бесплатного источника
кривой с приемлемой лицензией не найдено, а спот у EIA — первичный публикатор из
`knowledge/sources.md`.

### 24. Свои скиллы включаются автоматически, и это снимает одну страховку

Агенту включать скиллы по-прежнему нельзя: `skill_review`, `skill_preflight` и
`toggle_skill` в `DISABLED_TOOLS`, `/workspace/skills` объявлен защищённым путём. Но
владельцу возвращаться к этому при каждом запуске тоже не нужно: сервис `skill-enable`
(`scripts/enable_own_skills.py`) проходит по каталогам в `./skills` и закрывает оба условия
запуска — вердикт ревью и флаг включения — штатными owner-эндпоинтами
`POST /api/owner/skills/{skill}/attest-review` и `POST /api/skills/{skill}/toggle`.

Первый из них — owner-аттестация «Skip review» (v6.39): она пропускает дорогую фазу ревью
тремя ИИ-моделями, оставляя детерминированный preflight. Применима только к бакету
`external`, то есть ровно к скиллам этого проекта; `owner_attestable` для native и хабовых
скиллов равен false, так что расширить действие скрипта на чужие скиллы нельзя даже по
ошибке.

*Проявится:* вердикт ревью привязан к хешу содержимого, и раньше правка кода скилла
требовала осознанного повторного подтверждения человеком. Теперь очередной
`docker compose up` подтвердит новую версию сам. То есть изменение в `skills/`,
попавшее туда незамеченным, будет одобрено без участия человека.

*Почему терпимо:* в `skills/` пишет только человек — агенту запись в этот каталог
запрещена защищённым путём, и это проверяется отдельно от скилловой машинерии.

*Правильно, если понадобится строже:* сверять хеш содержимого с зафиксированным в
отслеживаемом git-файле и отказываться от аттестации при расхождении. Тогда правки
подтверждаются одной явной командой, а не молча. Не сделано: для одного доверенного
пользователя, который сам и правит эти файлы, лишний обряд без выгоды.

### 25. Каждый воркер грузит свою копию модели

Задачи выполняются не в процессе сервера, а в пуле отдельных процессов: в работающем
контейнере это сервер (~220 МБ), супервизор и около десяти воркеров. Все они называются
`python server.py` и различаются PID — на сравнении PID и построен `is_server_process()`
(`ouroboros/extension_companion.py:85`).

Расширение без изолированных зависимостей грузится in-process, то есть **в тот процесс,
который вызывает инструмент**. Значит и модульные глобали свои у каждого воркера — включая
прогретый пайплайн Chronos, ради которого мы отказались от `dependencies` (запись 19).

Измерено в контейнере на реальном прогнозе:

| Состояние процесса | Занято памяти |
|---|---|
| старт | 8 МБ |
| импорт модулей скилла | 25 МБ |
| + statsmodels, первый ETS | 164 МБ |
| + torch и веса Chronos | 646 МБ |

*Проявится:* воркер в покое занимает ~80 МБ. Первый прогноз в этом воркере поднимает его
примерно до 700 МБ и стоит 6–18 секунд. Память назад не отдаётся — пайплайн намеренно живёт
в глобали. Если запросы попадают в разные воркеры, счёт идёт на гигабайты.

*Чего, вопреки ожиданию, НЕ происходит:* глобальный лок расширений
(`_execution_lock` в `ouroboros/extension_isolated_deps.py`) пользователей друг от друга
**не блокирует**. Он объявлен на уровне модуля, то есть у каждого процесса свой, а
параллельные задачи расходятся по разным воркерам. Лок сериализует вызовы расширений только
внутри одного процесса. Значимым он становится там, где вызовы сходятся в один процесс —
у HTTP-роутов расширения, которые выполняются в процессе сервера. Это и есть довод против
`register_route` без кэша.

*Правильно:* кэшировать результат прогноза на диске. Тогда воркер, у которого ответ уже
посчитан, не грузит torch вовсе — а это как раз те 482 МБ и те секунды. Записано в `TODO.md`.

*Радикальнее:* `companion_process` — одна копия модели на контейнер, инструмент как тонкий
клиент. Дороже: свой IPC и свой жизненный цикл, см. запись 19.

*Почему сейчас терпимо:* пользователь один, задачи идут последовательно, реально
прогревается один-два воркера.

## Поиск по отчётам (skills/petro_rag/)

### 26. Порог отсечки не разделяет «есть в отчётах» и «нет в отчётах»

Замер на размеченном наборе (`reports/golden_dataset.jsonl`, 14 вопросов с ответом в
корпусе и 21 заведомо без него): у лучшего фрагмента для постороннего вопроса оценка
реранкера −0.43, а у части правильных фрагментов — −0.43 и −0.50. Диапазоны
пересекаются, то есть порога, который отсекает всё лишнее и не режет нужное, не
существует. С голыми эмбеддингами хуже: там косинус для всего лежит в 0.78–0.91.

Набор негативов расширен с 5 до 21 именно ради этого измерения: на пяти вопросах шаг
FP-метрики был 20 п. п., то есть грубее эффекта, который ей меряли. На двадцати одном
цена компромисса видна прямо: рабочий порог −0.5 даёт Recall 16/18 при 9/21 ложных, а
нуль ложных достигается только при +0.32, где Recall падает до 7/14. Полный разбор —
`skills/petro_rag/tests/README.md`.

*Проявится:* на вопрос вне корпуса («добыча в Пермском бассейне») поиск вернёт пару
фрагментов про добычу вообще. Если модель поленится прочитать их, она может выдать
нерелевантную цитату за ответ.

*Что сделано:* порог выбран в пользу полноты (−0.5), а решение отдано агенту — выдача
начинается с прямого указания «низкая близость означает слабое совпадение, не притягивай
нерелевантное», и в контракте ответа сказано честно говорить, когда отчёты темы не
покрывают. Пропуск факта из отчёта вреднее: он прямо нарушает требование «сначала
отчёты».

*Правильно:* обучить или подобрать калибровку на своём корпусе, а не брать модель
как есть. Не сделано: для 158 чанков и одного пользователя цена несопоставима.

### 27. Собранный корпус (140 документов) не индексируется

`ingest/` собрал 140 документов в `data/corpus/`, но `build_index.py` читает только
`reports/pdf/` — три PDF. Из корпуса 116 файлов HTML, у них нет страниц, и ссылка
«с. N» для них не собирается; нужен второй парсер и другой якорь цитаты (заголовок
раздела).

*Проявится:* агент уверенно отвечает по трём отчётам SberCIB и ничего не знает о EIA
STEO, которые лежат рядом на диске.

*Правильно:* читать `data/corpus/manifest.jsonl` — он для этого и задуман как
единственный вход индексатора — и добавить парсер HTML. Отложено сознательно: сперва
нужно было убедиться, что связка «поиск → цитата → ответ» вообще работает, на корпусе,
для которого есть размеченный eval.

### 28. Табличная вёрстка презентаций рвёт связь ячейки и подписи

Оставшийся промах поиска (Recall 89%, см. `skills/petro_rag/tests/README.md`) —
на слайдах, где значение лежит в таблице, а поясняющий текст отдельным блоком. При
извлечении текста из PDF порядок теряется, и чанк с числом не содержит слов, по которым
его ищут.

*Проявится:* вопрос «почему привилегированные акции Транснефти привлекательны» не
находит слайд, где ответ есть, потому что «Транснефть» и «маржа переработки» оказались в
разных чанках одной страницы.

*Правильно:* разбирать layout (pdfplumber или разметка таблиц), а не плоский текст.
Не сделано: заметно больше работы, чем выгода на трёх отчётах.

### 29. Индекс пересобирается целиком и вручную, а во время пересборки поиск лежит

Новый файл в `reports/pdf/` сам не подхватывается: нужен запуск
`scripts/build_index.py`. Пересборка всегда полная — коллекция удаляется и пишется
заново. На трёх отчётах (158 чанков) это около 100 секунд, почти целиком эмбеддинги.

*Проявится:* пока идёт пересборка, коллекции не существует, и `rag_search` возвращает
ошибку. Если агент в этот момент отвечает на вопрос, он уйдёт в веб и напишет, что база
отчётов недоступна. Время растёт линейно: корпус `ingest/` (140 документов, запись 27)
означал бы десятки минут недоступного поиска на каждую правку.

*Правильно:* инкрементальность по `sha256` — в манифесте `ingest/` хеши уже есть,
переиндексировать нужно только новое и изменившееся; и сборка в новую коллекцию с
атомарным переключением, чтобы поиск не проваливался вовсе.

*Почему сейчас не сделано:* корпус из трёх отчётов пересобирается за полторы минуты и
меняется вручную раз в несколько дней. Инкрементальность здесь — код, который сложнее
того, что он ускоряет.

### 30. Приоритет отчётов над вебом держится на промпте, а не на коде

Требование «сначала отчёты, веб — дополнение» выражено текстом в контракте ответа.
Никакой механики, которая заставила бы агента сходить в `rag_search` до `web_search`,
нет: порядок вызовов выбирает модель.

*Проявится:* на вопросе, который выглядит как «новостной», агент может уйти сразу в веб
и не заметить, что в отчёте есть более надёжная цифра. Тихо, без признаков ошибки.

*Правильно:* граф с жёстким порядком шагов вместо свободного цикла инструментов — но
это уже другой фреймворк агента, а не Ouroboros. В нынешней архитектуре максимум —
проверять постфактум, что в ответе на профильный вопрос есть хоть одна ссылка на отчёт.

### 31. Ответ, разорванный границей страниц, извлекается наполовину

Чанк не пересекает границу страниц (`skills/petro_rag/lib/chunking.py`), и плата за это
до сих пор была описана словами, но метрикой не ловилась: Recall останавливается на
первом попадании и засчитывает вопрос по любой найденной половине.

Метрика полноты фактов это измерила. Размечены шесть вопросов, ответ на которые
доказуемо лежит на двух страницах (12 обязательных фрагментов). На рабочем пороге до
агента доезжало **7 из 12**, при том что Recall считает попаданиями 16 из 18 вопросов.

*Проявится:* агент отвечает уверенно и с корректной ссылкой, но приводит половину
картины. У `hormuz-009` это выглядит так: найден вывод про замедление роста экономики на
0,5 п. п. (стр. 3), а инфляционный канал вреда со стр. 2 — нет. Ошибки в ответе не будет,
будет неполнота, которую нечем заметить.

*Где именно теряется — не на извлечении и не на ранжировании.* 11 фрагментов из 12
попадают в первую восьмёрку выдачи. Срезает их порог:

| Вопрос | Оценка первой половины | Оценка второй половины |
| --- | --- | --- |
| `oilgas-015` предложение нефти | +0.70 | +1.64 |
| `oilgas-017` спрос МЭА | +1.92 | +0.64 |
| `oilgas-016` ОПЕК+ март/апрель | +0.61 | **−0.80** |
| `oilgas-018` дно Goldman и сланец | +0.32 | **−0.77** |
| `hormuz-009` вред экономике | −0.42 | **−1.04** |
| `oilgas-005` факторы поддержки | **−0.61** | **−1.36** |

В четырёх парах из шести одна половина стоит высоко, а вторая заметно ниже: продолжение,
оторванное от своего контекста границей страницы, кросс-энкодер читает как менее
релевантное. Это и есть измеренная цена постраничной нарезки.

*Чего не хватило бы:* увеличения `top_k` — фрагменты и так в первой восьмёрке.

*Что сделано:* поиск дотягивает смежный кусок к тому, который порог уже прошёл, — не по
его собственной оценке, а как продолжение, и только когда текст на стыке действительно
оборван (`search._expand_torn_neighbours`). Полнота на пороге выросла с 7/12 до 10/12,
Anchor-Recall с 15/18 до 17/18, а Recall и ложные срабатывания не сдвинулись — и не
могли: дотягивание работает поверх того, что порог пропустил, и умеет только добавлять.

Попутно пришлось выбросить колонтитулы браузерной печати: они стояли между прозой
соседних страниц, и сосед у страницы 3 оказывался не текстом страницы 2, а строкой
«Стр. 2 из 3». Пока они были в индексе, дотягивание тянуло мусор и не давало ничего.

*Чего делать не стали:* склеивать соседние куски перед реранкером. Куски и так
ранжируются высоко, то есть реранкер их находит; склейка изменила бы оценки всем
фрагментам, включая проходящие с +1.64 и +1.92. Плюс склейка через границу страниц
сцепила бы несвязанные слайды презентации — ровно то, ради чего нарезка постраничная.

*Что осталось:* `oilgas-005` — единственный случай, где порог не проходит ни одна из
половин, поэтому дотягивать не к чему. Лечится только порогом или реранкером, а оба
трогать дороже: разбор цены компромисса в записи 26.

*Почему схему нарезки при этом не меняли:* размечено шесть вопросов из восемнадцати, и
четыре из них подобраны прицельно под разрывы страниц — это проба, а не доля по набору.
Её хватило, чтобы измерить потерю и починить её на стороне поиска, но не чтобы
перекраивать схему индекса. Сначала нужно разметить больше многостраничных случаев и
понять, насколько явление массовое.

## Сбор корпуса отчётов (ingest/)

### 17. Генерик-парсер listing/feed не видит JS-рендер и ссылки на HTML-статьи

`ingest/strategies.py` ищет только прямые `<a href="...pdf">`-подобные ссылки в статичном
HTML страницы-списка. Семь source из 24 (`IEA-007`, `EIA-003`, `EIA-009`, `EIA-012`,
`OFAC-001`, `CREA-001`, `SHELL-001`) при разведке 2026-08-09 не дали ни одной находки —
разбор по каждому в `data/corpus/probe-report.json` и в `ingest/README.md`. Причины
разные: PDF/CSV у EIA Petroleum Supply Monthly официально прекращены; Country Analysis
Briefs — интерактивный выбор страны без прямых ссылок на странице; CREA и часть Shell —
JS-рендер; IEA oil security и OFAC guidance ссылаются на HTML-страницы отдельных
материалов, а не на файлы.

*Проявится:* эти семь source в `python -m ingest.collect` стабильно показывают
`FAILED: стратегия не нашла ни одного выпуска` — это ожидаемо, не деградация.

*Правильно:* headless-браузер для JS-рендера плюс отдельный тип кандидата
("HTML-документ по ссылке с датой рядом", а не только файл с расширением) для
источников, ссылающихся на статьи. Не сделано: правило движка — общее решение на все
источники сразу, а не селектор под один сайт; headless-браузер — заметно больший скоуп
(новая зависимость, JS execution), чем эта итерация («только сбор файлов»).

### 18. Девять source закрыты как status: skip, reason: blocked — CDN/WAF, не обход

При разведке (`ingest/probe.py`, 2026-08-09) `opec.org` (все 5 позиций), `imf.org`,
`spglobal.com`, `unctad.org` отдавали 403/402 и честному User-Agent движка, и
стандартному браузерному (`curl -A "Mozilla/5.0 ..."`). `consilium.europa.eu` (EU-001)
особый случай: браузерный UA проходит через `curl`, но стабильно 403 через `httpx` — то
есть блокировка на уровне TLS/HTTP-стека (JA3-фингерпринт), а не строки заголовка.

*Проявится:* в каталоге эти источники значились Green/Open, но фактически недостижимы
для скриптового сбора; в частности выпадает OPEC MOMR — приоритетный ежемесячный
источник из исходного запроса.

*Правильно:* ничего в рамках этого движка — воспроизводить TLS-отпечаток браузера
(curl_cffi и подобное) или проходить JS-challenge Cloudflare/Akamai — уже подделка
защиты, а не честная идентификация. Записи сохранены в `registry.yaml` с `landing` и
`note`, решение переигрывается сменой `status` на `collect` одним словом, если у
издателя появится другой канал (партнёрский API, RSS и т. п.).

*Почему сейчас не сделали:* осознанное решение по правилу из design-плана сбора корпуса
— не изобретать обход бот-защиты.
