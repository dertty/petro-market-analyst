# Расчётный модуль прогнозирования цен на нефть

Даёт агенту-аналитику числа, посчитанные детерминированно, вместо прикидки в уме.
Оба инструмента возвращают JSON-строку, где рядом с числами лежит поле `interpretation`
с готовой формулировкой на русском и обязательными оговорками.

## Инструменты

**`forecast`** — прогноз спотовой цены на 1/3/6/12 месяцев.

Исторический ряд берётся из API EIA (серии `RBRTE` для Brent и `RWTC` для WTI),
кэшируется на сутки в каталоге состояния скилла; при недоступности API используется
снапшот из `data/`, и тогда ответ несёт явную пометку об этом. Ряд сводится к недельной
сетке, поэтому 12 месяцев — это 52 шага, один проход модели без авторегрессионной
раскрутки.

Методы:

1. **Chronos-Bolt** (`amazon/chronos-bolt-small`) — предобученная модель прогнозирования,
   применяется zero-shot и отдаёт квантили напрямую, без предположения о нормальности.
2. **Экспоненциальное сглаживание** Хольта с демпфированным трендом по лог-ценам —
   классический метод, интервал из статмодели, обратное экспонирование даёт корректно
   несимметричный коридор в уровнях цены.

Плюс **случайное блуждание со сносом** как бенчмарк. Он считается всегда и нужен для
проверки: если обе модели совпали с ним, содержательного прогноза направления нет ни у
одной, и интерпретация скажет об этом прямо.

Интервал везде **80 % (q10–q90)**, а не 95 %. Обученные квантили Chronos-Bolt
заканчиваются на 0.1 и 0.9, шире пришлось бы экстраполировать; считать один метод на
80 %, а другой на 95 % значило бы выдать несопоставимые коридоры.

**`supply_shock`** — диапазон цены при изменении добычи на N млн барр./сутки.

Это сравнительная статика, а не прогноз ряда: `ΔP/P ≈ −(ΔQ/Q) / (|η_d| + η_s)`.
Считается по трём веткам жёсткости рынка, и ответ обязательно возвращает сами
использованные эластичности вместе со ссылкой на работы, откуда взяты их диапазоны, —
иначе аналитик не сможет процитировать допущение.

**`demand_shock`** — диапазон цены при шоке спроса, симметрично `supply_shock`:
`ΔP/P ≈ +(ΔQd/Q) / (|η_d| + η_s)`.

Шок задаётся ровно одним из двух способов: изменением спроса напрямую (млн б/с) либо
изменением темпа роста мирового ВВП (п.п.), которое переводится в спрос через
эластичность спроса по доходу 0,5 (диапазон в литературе 0,3–0,8: Gately & Huntington
2002; IMF WEO апрель 2011, гл. 3; Hamilton 2009). Так ревизия прогноза ВВП из отчёта
агентства честно превращается в расчётный диапазон цены. Эластичность и источник
возвращаются в ответе, только когда маппинг из ВВП реально использовался.

**`macro_snapshot`** — свежий макрофон: качественный контекст поверх прогноза.

Семь структурированных рядов из публичных API без ключей; ни модели, ни LLM внутри нет —
только загрузка, арифметика дельт и кэш на три часа:

| Показатель | Источник |
|---|---|
| Индекс доллара (DTWEXBGS), ставка ФРС (DFF), CPI г/г (из CPIAUCSL), ожидания (T10YIE), индекс Килиана (IGREA) | FRED, `fredgraph.csv` |
| Курс USD/RUB (официальный) | ЦБ РФ, `XML_dynamic.asp` |
| Ключевая ставка | ЦБ РФ, SOAP `DailyInfoWebServ` |

По каждому ряду: последнее значение с датой, изменение за месяц и год, источник, пометка
о свежести и подсказка о знаке влияния на нефть. Каждая серия качается независимо:
упавший источник не роняет остальные, его данные берутся из прошлого кэша с явной
пометкой `stale_cache`. Принципиально: это **контекст, а не вход модели** — модель
прогноза одномерна и макрорядов не видит, наложение макрофона на прогноз — суждение
аналитика, и интерпретация инструмента говорит это прямо.

## HTTP-роуты для ручной проверки

Те же расчёты доступны по HTTP — чтобы проверять скилл, не поднимая агента:

```
GET /api/extensions/oil_price_forecast/forecast?benchmark=brent&horizon=3m
GET /api/extensions/oil_price_forecast/supply_shock?cut_mbd=2&spot_price=70
GET /api/extensions/oil_price_forecast/demand_shock?gdp_change_pp=-1
GET /api/extensions/oil_price_forecast/macro
```

Роуты зовут те же payload-функции, что и инструменты, поэтому возвращают ровно то,
что видит агент, — ради этого они и заведены.

Обработчики роутов **синхронные, и это принципиально**: асинхронный обработчик сервер
выполняет прямо на своём event loop и на время расчёта повесил бы весь HTTP-API рантайма.
Синхронный уходит в отдельный поток.

Две вещи, которые стоит знать, пользуясь ими:

- вызов роута грузит torch и веса **в процесс сервера** — замерено, со 172 до 772 МБ, и
  память не отдаётся до перезапуска; вызов инструмента грузит их в процесс воркера;
- на время расчёта удерживается глобальный лок расширений в процессе сервера, поэтому
  роут не предназначен для регулярного опроса — только для ручных проверок. Прежде чем
  вешать на него что-то автоматическое, нужен кэш результатов (см. `TODO.md`).

## Ограничения, которые нельзя опускать в отчёте

- Это выход статистической модели по ряду спотовых цен: не факт, не консенсус рынка и
  не фьючерсная кривая.
- Модели не знают о решениях ОПЕК+, санкциях и геополитике — такие факторы аналитик
  накладывает поверх сам.
- Спот EIA публикуется с лагом около недели; последнее наблюдение может не совпадать с
  сегодняшней котировкой.
- Эластичности в `supply_shock` и `demand_shock` взяты из литературы, а не оценены на
  этих данных. Запасы и стратегические резервы гасят шок и в формуле не учтены.
- Макроряды из `macro_snapshot` не входят в модель прогноза — это качественный контекст.
  IGREA публикуется с лагом около двух месяцев (это норма, а не задержка). Сервисы
  ЦБ РФ бывают медленными или троттлят зарубежные IP — тогда российский блок приезжает
  из кэша с пометкой `stale_cache`.

## Почему нет `dependencies`

Расчётный стек (torch CPU, `chronos-forecasting`, statsmodels, pandas, numpy) стоит в
образе рантайма, а не объявлен зависимостями скилла. Причины две.

Во-первых, изолированный `.ouroboros_env` не умеет ставить CPU-сборку torch: символ `+`
запрещён в имени пакета, поэтому `torch==X+cpu` не пройдёт, а `--index-url` задать негде.
Голый `torch` с PyPI притащил бы CUDA-сборку на несколько гигабайт.

Во-вторых, само наличие изолированных зависимостей переключает расширение в
out-of-process-режим, где `register()` и весь модуль выполняются заново на каждый вызов
инструмента. Веса Chronos перечитывались бы с диска каждый раз. Без `dependencies`
расширение загружается внутри процесса сервера один раз, и пайплайн живёт в модульной
глобали между вызовами.

Обратная сторона решения — падение torch уронит `server.py` целиком, и каждый вызов
удерживает глобальный лок расширений. Обе оговорки записаны в `PROBLEMS.md` проекта.
